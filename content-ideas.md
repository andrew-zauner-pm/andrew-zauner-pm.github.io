## Safe project summary pattern

Use this structure when publishing a generic project summary:

1. Context: Describe the type of business problem without naming the organization.
2. Challenge: Explain the technical or process issue in generic terms.
3. Approach: Describe the method, tools, or architecture at a high level.
4. Outcome: Share non-confidential impact using broad language.
5. Lessons learned: Include practical guidance that does not expose client details.

## Avoid

- Client names
- Revenue, margin, customer, vendor, employee, or transaction details
- Screenshots of actual dashboards, databases, tickets, or source systems
- Architecture diagrams that reveal a client environment
- Data model screenshots with table names from client systems
